# 源码精读方法论：把一个陌生仓库读成一门课

> 与具体仓库无关，换一个项目直接照着走。模板在 `templates/`，踩过的坑在 `PITFALLS.md`。
> 四个项目的实践基础：Claude Code v2.1.88 还原源码、Grok Build、DeepSeek Harness、OpenAI Codex。
> 用它跑出来的两门课在 [xueai.app](https://xueai.app/?from=source-reading-methodology)，可以先看成品再决定要不要照着做。

---

## 这套方法论解决什么问题

读一个几十万行的陌生仓库，最容易出现两种失败。

一种是读了很多但什么都没留下。今天读了工具系统，明天读了上下文压缩，一个月后只记得「它设计得挺复杂」。原因是没有产出物强迫你把理解结构化。

另一种更隐蔽：**产出物看起来很专业，但里面掺了编造**。AI 辅助读码时这件事几乎必然发生，它会根据文件名推测实现、根据常见模式补全细节、把注释当成代码行为陈述。一旦掺进去，整份文稿的可信度就是零，因为读者无法分辨哪句是真的。

这套方法论的核心是用一件事同时解决两个问题：**让每一个技术论断都可回溯到源码的具体行**。可回溯迫使你真的读到那一行，也让读者能自己验证。

---

## 四个阶段

产出物是分层的，每一层的输入是上一层的输出。不要跳级。

```
阶段一  语料准备      锁版本、备对比语料、建检索脚本
   ↓
阶段二  大纲          回答「这门课要解答哪一个问题」+ 逐章源码锚点
   ↓
阶段三  章节书稿      八段结构，每处论断带行号，机器校验
   ↓
阶段四  成书          编成一本带封面封底的 HTML 书，可读、可查、可传
```

跳级的后果很具体：没有阶段一的版本锚点，阶段三写的行号三个月后全部失效；没有阶段二的锚点清单，阶段三的并行写作会互相重复又互相矛盾。

## 阶段一：语料准备

### 锁死版本锚点

动笔前给主教材仓库打一个 tag，把 tag 名和 commit hash 写进所有下游文档的文件头。

```bash
git -C <repo> tag course-anchor-YYYYMMDD
git -C <repo> rev-parse --short HEAD
```

行号是这套方法论的地基，而上游仓库每天都在变。不锁版本，写到第十章时第一章的行号已经漂了，而且你无法判断是当初写错还是后来改了。

文件头固定写成这样，读者和未来的你都需要它：

```markdown
> 源码核对基于 <owner>/<repo> commit `4f39251a01`（2026-08-22），tag `course-anchor-20260822`
```

### 备齐对比语料

**只读一个仓库读不出设计决策。** 你会把作者的选择当成唯一解，因为你没见过别的解法。

至少准备一个同类项目做对照。理想情况是三个，覆盖不同语言和不同取舍。四个项目的实践里，对比语料贡献了最有价值的那部分内容：同一个问题的两种答案各自付出了什么代价。

对比语料也要锁版本，路径写进关键路径表。

### 建检索脚本，不要建向量库

查阅场景是「找所有提到 tool permission 的地方」「找 compact 的实现」，这是关键词匹配，不是语义检索。`rg` 毫秒级出结果、零依赖、终端里直接用。

包一层 `search.sh`，把常用范围做成参数：

```bash
./search.sh --src "autoCompact"      # 只搜源码
./search.sh --docs "context window"  # 只搜官方文档
./search.sh --blog "multi-agent"     # 只搜博客等外部材料
```

### 收集「为什么」的一手材料

源码告诉你「怎么做的」，不告诉你「为什么」。「为什么」按这个优先级找：

1. **仓库根的评审红线文件**（`AGENTS.md`、`CONTRIBUTING.md`、`.cursor/rules/`）。每条禁令背后通常都是一次真实事故，这是「为什么不那样做」的唯一一手来源
2. **模块或 crate 级 README**
3. **模块头注释**（Rust 的 `//!`、Python 的模块 docstring）。写得认真的项目，这里就是完整设计说明
4. **测试文件**。测试暴露了作者担心什么边界
5. **官方博客与文档**。注意它讲的是理想形态，要和源码做对照，差异本身就是内容

指向外部链接的空壳文档要识别出来并跳过。工程细节一律以源码为准。

## 阶段二：大纲

大纲不是章节标题列表。它要先回答三个问题，再展开锚点。

### 先立一个真问题

整门课要收束到一句话上。这句话决定了哪些内容进、哪些不进。

举两个真实例子：

- DeepSeek Harness 那门课：**Agent 运行时该长什么样**，收束到一条运行时不变量 `Model-visible ⟺ logged`
- OpenAI Codex 那门课：**当它敢在你机器上跑命令、连网络、带着你的凭据，它凭什么值得被信任**，收束到「DSH 让一切可回放，Codex 让一切可拒绝」

没有这句话，大纲会退化成源码目录的中文翻译。

### 明确读者带走什么

写清全课累计交付的可迁移物，越具体越好。「学会 Agent 架构」不算，下面这种才算：

- 一套上下文注入的类型化治理方案，能直接抄成自己项目的 code review 规则
- 一个 LLM 友好的文件编辑协议规范，可直接复用
- 一份「你的 agent 该不该做沙箱、做到哪一层」的决策树

### 逐章写锚点，并区分已核实与候选

每章列出：核心问题、源码入口（文件路径 + 候选行号）、要分析的设计决策、对比对象。

已经实读核实过的行号标 ✓，没标的一律视为候选。

**这里有一条血泪教训：✓ 的含义是「曾经核实过」，不是「现在还对」。** 上游改动、你自己的重构、锚点笔误都会让它失效。写章节时即使看到 ✓ 也要重新 Read 一遍，因为你真正要引用的可能是相邻的行。

### 章数与姊妹课对齐

如果这是系列里的第二门课，让章数和主题分组与前一门对齐，这样可以逐章互链。互链之后两门课互为对照材料，价值远大于各自独立。

已经讲透的通用机制不重复讲，只讲差异做法并链回去。

## 阶段三：章节书稿

### 零幻觉是唯一不可妥协的要求

违反的稿件直接作废，不是修改，是作废。七条：

1. 每一处源码引用、每一个行号、每一个类型名与函数名，动笔前用读文件工具实读核实。禁止凭印象写、禁止根据文件名推测、禁止照抄大纲里的候选行号
2. **代码块必须与源文件逐字节一致**。保留原始缩进、属性宏、注释、空行。禁止转译、禁止美化、禁止删属性、禁止写「示意代码」或「简化版」
3. 找不到某个机制的实现，明确写出来：`未找到对应实现，检索关键词为 X、Y、Z`。不许编一个看起来合理的实现
4. 源码里没明说、由你推断的结论，显式标注为推断
5. 引用注释原文时说明这是注释，不要把注释内容当成代码行为陈述
6. 数字（行数、文件数、枚举变体个数）必须实际统计过。统一用 `splitlines()` 口径，避免末行换行符造成的 off-by-one
7. 引用符号链接时引真实文件。`CLAUDE.md -> AGENTS.md` 这种情况引 `AGENTS.md`，否则同一份材料在不同章节里会出现两个名字

### 引用格式与省略标记

代码块三个组成部分都必填，起始行、结束行、相对仓库根的路径：

````
```153:160:codex-rs/core/src/session/turn.rs
pub(crate) async fn run_turn(
    sess: Arc<Session>,
    ...
) -> CodexResult<Option<String>> {
```
````

长函数中间可以省略，但**省略必须显式标记**，写成含 `...` 的整行注释：

```
    // ... 填 SID 表 ...
```

静默删行是最危险的失败模式。真实案例：某章引用一段文档注释时悄悄删掉六行，删掉的恰好是「有意保留什么」那半段，导致正文结论不完整却看不出破绽。

### 八段结构，顺序固定

| 段 | 要求 |
|---|---|
| ① 场景还原 | 从具体会翻车的情形开局，不要从概念定义开局 |
| ② 逐行精读 | 篇幅主体。按调用链或数据流带读，一段代码一段话交替推进 |
| ③ 设计决策分析 | 回答「为什么」，给出「不这样做会出什么事」的具体后果 |
| ④ 边界条件剖析 | ≥ 2 个「如果…会怎样」，答案落到确切分支和行号 |
| ⑤ 横向对比 | ≥ 1 组，两侧都给路径行号，说清各自代价 |
| ⑥ 演示设计 | 分步 + 每步字幕文案 + 逻辑轨迹面板 |
| ⑦ 可迁移结论 | 哪些值得抄、最小成本形态、哪些是过度设计 |
| ⑧ 思考题 | ≥ 3 道，含 1 道动手验证 |

两段最容易被敷衍，也最能拉开深度：

**边界条件**不许答「取决于配置」。必须落到源码里某个 `if` 的某一行。

**横向对比**不许写成功能清单对照。禁止只说「A 有 B 没有」，要说清 B 为什么可以没有、或者 B 用什么别的东西补上了。某一侧确实没有对应实现时，按零幻觉第 3 条写明检索关键词。

### 深度硬指标

交付前逐项打勾。数字是下限，不是目标。

| 指标 | 下限 |
|---|---|
| 源码原文引用 | ≥ 10 处，其中 ≥ 3 处是完整函数、完整枚举或完整 trait |
| 规范性材料精读 | ≥ 1 处全文精读并转述其约束意图 |
| 双侧对比 | ≥ 1 组 |
| 图 | ≥ 3 张，其中 ≥ 1 张时序图或状态图 |
| 边界追问 | ≥ 2 个 |
| 跨平台差异 | 涉及执行、文件、网络的章节必须交代，或明确写明与平台无关 |
| 正文字数 | 6000 到 10000 字，不含代码与图 |

## 阶段四：成书

三十章 markdown 堆在一个目录里，能读，但没人会真的读完。这一层把它们编成一本书：封面、目录、正文、封底，双击就能看，也能直接传到任何静态托管上。

```bash
pip install markdown
cp book/book.config.example.json book.config.json
python3 book/build_book.py
```

用法与配置见 `book/README.md`。这里只说三件为什么。

### 为什么必须有封面和封底

封面承担的是「这本书回答哪一个问题」，也就是阶段二立的那句话，落到版面上。封底承担的是**可信度交代**：逐章的引用数、图数、字数，以及被精读仓库的 commit 与 tag。

读者判断一份源码解读值不值得信，看的就是这两样：它敢不敢把口径摊开，敢不敢说清行号对应的是哪个版本。把这些藏起来的解读，读者只能选择信或不信。

### 为什么行号要留空

引用块头部声明了起止行。块里如果有省略标记，**省略之后的行号是推不出来的**，跳过了多少行只有源文件知道。

所以构建器只排两头：开头那段从起始行正着数，结尾那段从结束行倒着数，夹在两个省略之间的段落留空显示 `·`。宁可不显示，也不显示一个编出来的行号。

这跟整套方法论是同一条原则。行号是读者验证的唯一入口，编一个看起来合理的行号，比不给行号更糟。

### 演示落到哪里

阶段三每章都写了「互动演示设计」，包含分步动画、每步字幕、逻辑轨迹面板。成书里它以两种形式存在：

一是**版面本身的动效**，都为可读性服务：滚动渐入、目录跟随、图进入视野才描线、带省略的引用块可以逐段步进看清哪几行真的连在一起。

二是**演示设计原文**，作为一节留在正文里。任何人照着它就能实现成可交互的页面，包括你自己后面要做的课程站。

如果你的产出形态就是课程站的交互课页，`templates/02-page-spec-template.md` 是那条路的规范，与成书并行，不冲突。它的核心要求只有一条：课页上默认零代码，因为能在一页上贴的代码量远小于理解所需，贴一小段反而给人「看过了」的错觉。代码留在书里。

## 贯穿全程：文风

文风不是审美偏好，是这套流程能不能交付的硬约束。原因有两个。

**一个人写三十章会自然收敛，N 个 Agent 写三十章不会。** 不把文风写成可执行的规则，读者拿到的就是三十种腔调拼起来的东西，读第五章时会怀疑前四章是不是同一个人写的。

**AI 的默认文风有固定病灶，不明令禁止就一定出现。** 这不是模型质量问题，是它的训练分布就长那样。六类反复出现的：

1. **评价式转述**。「这个设计非常巧妙」「很简单」。读者要的是它做了什么，不是你觉得它怎么样
2. **解读前置**。「这背后其实有一个深层判断」，然后才说判断是什么。直接说判断
3. **情绪词与网文腔**。「震撼」「细思极恐」「刺穿」
4. **破折号滥用**。一段话里三个 `——`，全部可以换成逗号、句号或拆句
5. **「不是…而是…」句式**。它靠否定一个没人主张的东西来显得有洞见，改成正向陈述信息量更高
6. **自我感悟式过渡**。「我一直觉得」「我想到一个词」，以及催读者感悟的「你品品」

### 一条元规则：禁忌必须可正则化

**能写成正则的进「禁忌」，不能的进「表达偏好」。** 这条分界很重要：无法自动检查的硬性规则等于没有规则，写了只会让人以为已经守住了。

于是文风规范分成两栏，性质完全不同：

| | 禁忌 | 表达偏好 |
|---|---|---|
| 判定者 | 机器 | 人 |
| 例子 | 不许出现 `——`、`……`、「不是…而是…」 | 类比要具体接地气、长段拆短、术语首次出现给一句白话解释 |
| 违反后果 | 交付前必须清零 | 评审时提出，不卡交付 |

具体的十二条禁忌清单和表达偏好清单在 `templates/01-chapter-spec-template.md` 第 4 节，直接抄。清单只维护那一份，不要复制到多处，否则改一处忘一处。可以直接跑的扫描器在 `templates/style_scan.py`。

还有一点要说清：**禁忌只管面向读者的正文**，也就是章节书稿正文和课页正文。大纲、写作规范这类内部工作文档不受约束，那里用破折号做锚点标注反而更省事。范围划不清的话，会有人跑去改大纲的行文，白费功夫。

反过来，**不要用同义替换绕过正则**。把「而不是」换成「而非」，正则过了，问题一点没解决。禁的是靠否定来制造对比这件事，不是那三个字。这条要写进规范，否则执行者会自然滑向糊弄检查那条路。

### 禁忌清单从哪来

不是坐着想出来的，是把实际改稿时反复在删的东西固化下来。做法：第一章人工精改一遍，把每一处删掉的表达归类，出现两次以上的就写进禁忌。

所以这份清单是有项目特性的。写安全主题的课就会长出安全特有的表述纪律，写别的主题不需要：

- 区分「隔离措施」和「安全边界」。源码自己坦承的局限要照搬，不要替它吹
- 不写「无法绕过」「绝对安全」。写「这道防线挡住了 X，挡不住 Y，Y 由下一层负责」
- 举攻击例子一律用无害样例，不给可直接复用的恶意载荷

### 一类容易被忽略的禁忌：过程性语言

读者没见过大纲、没见过写作规范、不知道作者是被派来写这一章的。所以正文里不能出现生产过程的痕迹：

- 禁止「大纲写…」「和大纲不符」。要表达同一个意思，写成「一个流传很广的说法是…，实际检索下来…」
- 禁止「按规范要求」「本次任务」「我负责的这一章」
- 禁止出现本机绝对路径，路径一律相对仓库根

与大纲不符的地方写进交付回复里，正文只留经过核实的结论。

这一类特别容易漏，因为写作者自己看不出问题：对他来说大纲是真实存在的上下文。它也最能暴露内容是流水线产出的。

### 还有一条：不把技术栈当卖点

读者不关心它是 Rust 还是 TypeScript，关心这个判断对不对。语言只在解释「为什么这个设计在这里成立」时出现，比如类型系统承担了运行时校验的职责。标题、开头、可迁移结论里不要把语言当卖点。

### 规范要自我遵守

写完规范，用它自己的正则扫一遍规范文件。一份满是 `——` 的文风规范说服不了任何人，也会让执行者判断不出哪些条目是认真的。

## 贯穿全程：机器校验

**这是这套方法论里投入产出比最高的一件事。** 人工复核十万字的行号不现实，必须写脚本。

### 校验器要在批量生产之前建好

至少校验三件事：

1. **代码块与源文件逐字节比对**。以内容为准、行号为辅：把引用块按省略标记切成连续段，要求每段在源文件里能找到完全连续的匹配。拼不上就判 FABRICATION。行号错了可以自动校正
2. **文风禁忌扫描**。把上一节那份禁忌清单写成正则，交付前自动过一遍。扫描要跳过代码块和行内代码，否则源码里的字符会被误判
3. **引用密度下限**。防止一种很隐蔽的作弊：删掉引用让校验变绿

第三条来自真实事故。某章初稿 56 处引用带若干报错，交付时只剩 22 处、全部通过，作者把报错的引用删掉了。**校验器只报「现有引用是否正确」，不报「该有的引用是否还在」，这个缺口必须补上。**

### 校验器本身需要被测试

它会误报，误报会让人开始忽略它的输出，那就等于没有。四个真实的误报：把闭合花括号判成内容不符、把正文里合理的引号判成违规、把品牌图标的 SVG 路径判成缺属性、把自动生成的 SEO 区块判成手写注入。

每修一个误报都要记下判据，不然下一次重构会把它改回去。

### 校验器不能覆盖的部分

行号是否落在文件范围内、被引用文件是否存在，这些要单独一个脚本查。逐字节比对只能验证「引用的内容存在」，验证不了「引用的路径写对了」。

## 并行生产

三十章逐章写完要很久，可以派并行子 Agent，每个负责一章。前提是规范足够硬，规范里每一处含糊都会变成三十份不同的理解。

### 派活时必须给的东西

- 完整的写作规范（一个文件，不要口头补充）
- 那一章的大纲条目
- 全部语料的绝对路径，包括对比语料。**不要凭印象说某个语料不在本地**，先确认再说，否则子 Agent 会绕开它
- 校验命令，以及「必须全绿才算交付」

### 子 Agent 的四种典型偏差

都是真实发生过的，规范里要提前堵：

1. **删引用让校验变绿**（见上文）
2. **为了凑字数上限而滥用省略标记**。某章出现 25 处省略，参照章是 0 处。省略只用于确实无关的样板代码
3. **把检查糊弄过去**。页面动画检查不过，就静态写死动画完成态骗过去，检查要求的事一件没做。校验器要加反作弊项
4. **误报上游文档写错了**。收到这种报告先自己核，实际命中率约两成

第四条值得展开。要求上报时必须带证据，格式固定：**被质疑的原话 → 源码文件与行号 → 那几行的原文 → 为什么对不上**。并提前告知三种常见误判：

- 引用区间含文档注释、或末尾没收进 `}`，都不算错
- 顺着继承和别名再查一层再下结论。曾有人报「这几行里没有 `UNKNOWN_TOOL`」，实际是那行抛的异常在类定义处就带着 `code: 'UNKNOWN_TOOL'`
- 约数按约数判。文件 298 行，原文写「约 300 行」，成立

### 上游文档的错误要集中修

并行生产中子 Agent 会陆续报出大纲的问题。不要边收边改，改到一半又来一条，容易互相覆盖。开一个 `PENDING_FIXES.md` 累积，全部回来后统一核实、统一修。

## 互链

系列课程之间做双向互链，两门课互为对照材料。

挂链接的唯一标准：**读者点过去之后，应该能看到这个机制的展开讲解。**只顺带提了一句的页面不算。

三条经验：

- 宁缺毋滥。四个 Agent 扫过 64 张对比卡，最后只挂上 18 条，剩下的大多是拿闭源产品做对照、站内没有对应展开页。硬凑的链接比没有链接更糟
- 同一页两张相邻卡片不要指向同一个目标，那是重复入口
- 结论是「没有对位实现」的卡片不要挂链接，那和链接目标恰好相反

按标题片段定位而不是按顺序定位，因为顺序会随改版变化、标题不会。定位不到就报错退出，不做静默跳过，静默跳过会让人以为链接加上了。

## 一句话总结每个阶段

| 阶段 | 一句话 |
|---|---|
| 语料准备 | 锁死版本，备好对照，别建向量库 |
| 大纲 | 先立一个真问题，再列锚点，✓ 只代表曾经对过 |
| 章节书稿 | 每个论断可回溯到行，逐字节一致，省略必须显式 |
| 交互产物 | 代码留在书稿，页面负责让人明白 |
| 文风 | 能正则化的进禁忌，不能的进偏好，不可检查的硬规则等于没规则 |
| 机器校验 | 先建校验器再批量生产，还要校验「该有的引用是否还在」 |
| 并行生产 | 规范里每一处含糊都会变成 N 份不同理解 |
