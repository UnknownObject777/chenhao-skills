# 阶段二的成品：大纲长什么样

> 这是一份真实大纲的两处节选，源项目是 openai/codex（Rust 单仓，90 多个 crate）。
> 对照 `../templates/00-outline-template.md` 看，能明白每个占位符该填到什么程度。

大纲要先立住定位，再逐章写锚点。下面第一段是定位，第二段是第 1 章的锚点条目。

---

## 一、定位部分

注意它没有直接列章节，而是先回答「这门课解答哪一个问题」，并把答案收束成一句话。这句话决定了后面哪些内容进、哪些不进。

## 课程定位

DSH 那门课回答的是「Agent 运行时该长什么样」。这门课回答的是它的下一个问题：

> **当这台运行时真的敢在你的机器上跑命令、连网络、改文件、还带着你的凭据，它凭什么值得被信任？**

Codex 是目前公开源码里，把「信任」这件事做得最重的 agent。90 多个 crate 里有超过十个只服务于一件事：确定这一条命令能不能跑、以什么身份跑、能碰哪些路径、能连哪些域名、凭据要不要给它看、出事了谁来兜。DSH 用一条运行时不变量（`Model-visible ⟺ logged`）撑起整个系统的可审计性，Codex 用类型系统、策略 DSL、三套操作系统沙箱和一个专门的审查模型撑起整个系统的可控性。

两条路各有代价，这门课把代价摆出来。

### 与 DSH 专题的关系

不重复讲 DSH 已经讲透的通用机制（事件溯源、插件树、Inbox 三语义、Token 计量投影）。凡是两边都有的机制，本课只讲 Codex 的差异做法并链回 DSH 对应课页；凡是 DSH 没有的（沙箱三平台、Guardian、网络与凭据代理、竞品迁移、Realtime），本课展开讲。

课程最终收束到终章的一句话对照：**DSH 让一切可回放，Codex 让一切可拒绝。**

### 读者带走什么

每章结尾的「可迁移结论」必须落到读者自己的项目上。全课累计交付：

- 一套上下文注入的类型化治理方案（能直接抄成自己项目的 code review 规则）
- 一套命令审批策略的写法（策略文件自带测试用例这个技巧可独立使用）
- 一份「你的 agent 该不该做沙箱、做到哪一层」的决策树
- 一个 LLM 友好的文件编辑协议规范（apply-patch 格式可直接复用）
- 一份 Code Mode 上不上的成本清单

## 二、逐章锚点部分

一章一条，五个固定字段：核心问题、源码锚点、对比锚点、边界条件示例、互动演示。

行号后面标 ✓ 表示当时实读核实过。写作时即使看到 ✓ 也要重新读一遍，因为真正要引用的可能是相邻的行。

### 第 1 章：90 个 crate 与一条「不许往核心加代码」的禁令

**核心问题**：一个 agent 运行时长到 90 个 crate 时，靠什么阻止核心继续膨胀？

**Codex 锚点**：
- 全仓 crate 清单与规模分布（`tui` 27 万行、`core` 20 万行、`app-server` 5 万行、`core-plugins` 4.2 万行，其余 80 多个各自几千行）
- ✓ `AGENTS.md:72-83`「The `codex-core` crate」一节全文精读：**resist adding code to codex-core**，新概念优先找别的 crate 或新建 crate，评审时要主动 push back
- ✓ `AGENTS.md:49-61` 模块体量治理：目标 500 行、超过 800 行必须开新模块，并点名了五个高频冲突文件（`tui/src/app.rs`、`chat_composer.rs`、`footer.rs`、`chatwidget.rs`、`bottom_pane/mod.rs`）
- ✓ `AGENTS.md:125-131` 单次改动不超过 800 行，复杂逻辑不超过 500 行，超了要拆成可评审的阶段
- 双构建系统：Cargo + Bazel 并行，`MODULE.bazel.lock` 154 万行，`AGENTS.md:37-43` 说明改依赖必须同步刷新 lock、`include_str!` 必须同步改 `BUILD.bazel`

**对比锚点**：
- DSH：56 包插件树 + Cordis 时空可组合性（`dsh-1`）——DSH 用架构强制解耦，Codex 用评审规则强制解耦，两种做法的成本与失效模式
- Grok Build：60+ crate 的 Rust 组织方式，同语言对照

**边界条件示例**：`core` 明明已经 20 万行，禁令是什么时候立的、之前的债怎么还？（从 git log 找禁令引入时间与随后的拆分 commit。）Bazel 与 Cargo 判定不一致时以哪个为准？

**互动演示（Demo 1·模拟器）**：crate 依赖体检台——把 90 个 crate 画成力导向图，节点大小是代码行数，读者点「假装往 core 加一个功能」，动画展示依赖边如何蔓延、哪些下游被迫重编译；再点「按禁令新建 crate」，对比蔓延范围。侧栏实时显示两种做法的增量编译时间估算。

## 从这份条目里能看出的三件事

**锚点要具体到行。** `AGENTS.md:72-83` 这种写法让写作 Agent 不用自己找料，直接去核实。锚点越具体，后面并行写作的一致性越高。

**对比对象在大纲阶段就定死。** 不要留到写作时自由发挥，否则三十章会出现十章都在跟同一个项目对比同一个点。

**演示方向在大纲阶段就分配。** 这里写的是「crate 依赖体检台」，别的章各有各的方向。不提前分配，多个写作 Agent 会做出雷同的演示。
