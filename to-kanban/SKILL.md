# 个人时间规划看板

围绕用户当期最想推进的事情安排时间。月定方向，周定成果，日定行动；每个周期重新判断主要矛盾，不把月任务机械平分到每天。

覆盖用户纳入规划的科研、学习、工作和生活。健康、休息、必要事务可以独立存在，不必强行包装成主目标的子任务。

**REQUIRED SUB-SKILL:** 使用 `primary-contradiction`，从当前技能目录发现并完整读取。缺失时说明，先收集诉求，暂停主要矛盾判断；不得声称已调用。它负责分析方法，本技能负责周期、确认、容量和看板。

## 先问诉求，再分析和排程

按可观察的对话状态前进。用户认可技能设计，不等于已确认某个月、某周或某天的个人诉求。

| 当前状态 | 本轮输出 | 停在哪里 |
|---|---|---|
| 新周期，尚未确认当期诉求 | 一批关键问题，诉求放第一位 | 等用户回答，不给任务清单、看板或先做建议 |
| 诉求已确认，主要矛盾未确认 | 矛盾分析与请用户确认的问题 | 不排程、不生成看板 |
| 本周期诉求及主要矛盾均已确认 | 按已知容量生成或更新看板 | 不扩展到未请求的周期 |
| 原诉求、截止日期或精力发生实质变化 | 重评受影响周期，请用户确认 | 再修改受影响的任务 |

首次默认一批 5 个问题，每个问题附一个简短的回答建议；信息已给出时只问缺项，最多 5 个，不为凑数重复提问。推荐回答方式，不替用户填个人事实。用户偏好批量提问，不能被其他访谈技能的一次一问覆盖。

1. **主要诉求**：这段时间最希望发生什么变化，怎样算有进展？建议先说最重要的一件事，也可以回答暂时不清楚。
2. **周期**：要规划哪个月、哪一周或哪一天？建议给起止日期，说明需要哪些层级。
3. **硬约束**：有哪些真实截止日期和不能挪动的安排？建议区分外部截止与自己希望完成的日期。
4. **容量**：扣除固定安排后，大约有多少可用时间，近期精力怎样？建议给范围，允许回答未知。
5. **候选事项**：哪些待办、旧任务和生活事务要一起考虑？建议贴现有清单或看板，标出不能牺牲的事项。

用户已清楚表达诉求时简短复述，不再要求重填问卷。用户说诉求不清楚时，用其真实材料协助澄清，给可供修正的候选，不自行确定优先级。历史任务或记忆只能辅助，不能代替本周期确认。赶时间时缩短问题，仍先获得诉求；不要先塞一张“临时看板”。

## 每个周期单独找主要矛盾

每次分析对象是“在这个周期、这些约束下，实现已确认的诉求”。按 `primary-contradiction` 执行，并把结果简短写成：

- **诉求**：用户确认的预期变化。
- **主要矛盾**：明确的 `X ↔ Y`，不是“论文”“效率”或一串待办。
- **判断依据**：用户提供的哪些事实支持它；说明是否满足决定走向、牵动全局、一通百通中的至少两条。
- **次要矛盾及反向验证**：主要矛盾解决后，各自会消失、降级还是照旧，并说明原因。多数照旧时重判，不能硬称“一通百通”；仍无法判断就提出缺失信息或待验证假设。
- **先动哪里**：一个处理方向，尚未确认时不把它变成任务安排。
- **确认**：请用户确认或修正本周期判断，然后停下。

月、周、日可以有不同的主要矛盾。日程里出现硬截止或精力下降时，解释为何需要调整；不要擅自改变已确认的月目标。生活维持和独立义务不必因主矛盾缓解而消失。

## 把确认后的判断变成行动

| 层级 | 卡片内容 | 与上级的关系 |
|---|---|---|
| 月 | 本月希望得到的具体成果及完成标准 | 对应本月诉求，不预填未来每天的矛盾 |
| 周 | 本周可交付的阶段成果及估算投入 | 主线卡引用对应月卡；独立义务注明原因 |
| 日 | 当天可完成的具体行动、预计用时、完成标准 | 主线卡引用周卡；必要时缩小到可执行的一步 |

只细排有足够信息且已确认的周期。仅请求今日时不额外生成整月文件。缺少上级看板时标“上级未建立”，不编造链接；用户要求联动规划时，可先确认月、周、日判断，再生成相应文件。批量规划也不能替未来每一天虚构诉求、精力和主要矛盾。

排程先保留用户的固定安排、休息和必要事务，再把精力较好的时间留给主线行动。硬截止任务即使是次要事项也要显式处理。建议每天突出一个最重要的行动，其余按实际容量取舍。

写清可用时间、计划投入和缓冲。任务用时属于估算，不能冒充用户提供的事实；不把估算写成完成保证。计划投入加缓冲不得超过可用时间。容量未知时允许生成“待估时”的候选卡，不作每日负荷承诺，不擅定几点开始。建议安排日期与真实截止分别标注。

父成果与子行动不是两份工作，不重复累计工时；子卡完成不自动等于父成果完成。完成与否以对应验收标准为准，不因日期经过就打勾。日行动不再受原版“1～3 天开发链路”、FE/BE 配对、负责人或 icafe 规则约束。

## 生成与更新

**生成文件前必读** [references/board-format.md](references/board-format.md)，按其中的目录、卡片身份、状态列和示例输出。

默认一月一板、一周一板、一天一板。周期体现在文件名与属性里，列只表示任务状态，避免把“周一、进行中、月底”混作同一维度。

用户给出 vault 与目录后，仅访问和修改相关文件；目标未知时先提供聊天中的 Markdown 或当前工作区的交付文件，并说明尚未写入 vault。不搜索所有私人笔记，不安装插件，不创建提醒或自动化，除非用户另有明确请求。

更新前读已有文件，保留手工笔记、卡片身份、完成状态和插件设置。遇到冲突先说明。规划工作不等于执行卡片中的任务。

## 周期复盘与转入

再次规划时先确认本期诉求是否变化。对旧卡逐项记录“未完成原因、当前价值、处理建议”，再由用户确认继续、缩小、推迟或取消。原因未知就标未知，不诊断为懒惰。

继续的卡只计算剩余投入，保留来源链接和转入去向；取消不等于完成。不批量顺延所有未完成项，不删除原记录，不重复统计同一行动。主矛盾变化时重新判断旧任务的价值。

## 常见错误与检查

| 错误 | 应做的事 |
|---|---|
| “先给个能启动的版本”就直接排一周 | 先问诉求和缺失约束，等回答 |
| 输入列了论文，就认定论文最重要 | 请用户确认本期重心 |
| 用三段日期切块替代月周日联动 | 分周期文件、引用上级成果、按容量拆行动 |
| “没做完就顺延” | 先审查原因、价值与剩余投入 |

交付前检查：本期诉求及矛盾确已确认；判断有事实依据；承诺量不超容量；日期与估算没有伪装成事实；主线卡有真实上级或明确缺项；生活义务未被遗漏；旧状态未被覆盖；看板语法符合引用规范。
